## 調査で確認した事実

以下は 2026-10-12 時点のコードと文書から確認した事実です。判断や推奨は含みません。

Tab (0x09) は、Linux の termios による raw モードでも、Windows の `ENABLE_LINE_INPUT` を外したコンソール入力でも 1 バイトとして届きます。  
現状は `read_key()` (`prompt.c`) と `pinned_prompt_read_key()` (`pinned_prompt.c`) の `c >= 0x20` の判定から外れ、`KEY_UNKNOWN` として無視されています。  
そのため、Tab に新しい動作を割り当てても既存のキー操作とは衝突しません。

生成オプション `cplat_prompt_options` は `flags`、`reserved`、`size_t` 3 項目で構成され、`flags` と `reserved` は「0 を指定」と記載されています。  
実装は `flags` と `reserved` を参照していません。構造体へ項目を追加すると構造体のサイズが変わり、既存の利用側とのバイナリ互換性が崩れます。  
一方、`cplat_prompt` と `cplat_pinned_prompt` のハンドルは中身を公開していない型のため、内部の状態を追加しても互換性は崩れません。

prompt と pinned_prompt は、キーの読み取りと編集処理をそれぞれ別に実装しています。  
両者が共有する処理 (UTF-8 文字境界、バッファー拡張、初期値の検証) は `prompt_edit.c` にまとめられています。

pinned_prompt の readline は、キーを 1 つ読み取るたびに `cplat_local_lock` で排他制御を行います。  
`cplat_local_lock` の Windows 実装は `SRWLOCK` を使用しており、同じスレッドからの再取得はできません。

テストは `TESTING.md` に記載のとおり、`prompt_edit.c`、`prompt.c`、`pinned_prompt.c` の行カバレッジと条件網羅 (C2) がいずれも 100% です (2026-09-26 計測)。  
`promptPlatformFake` により、実端末を使わずにキー入力列を与えて試験できます。

サンプル コマンド `prod/src/cmd/pinned-prompt/pinned-prompt.c` は pinned_prompt を使う対話コマンドで、`start`、`stop` などの命令を受け付けます。

版 2 で追加調査した事実は次のとおりです。

prompt の再描画 (`prompt.c` の `redisplay()`) は、行頭へ戻って入力を書き直し、`ESC [ n D` でカーソルを左へ戻します。端末の幅は取得していません。  
そのため、入力が端末の幅を超えて折り返すと、カーソルを戻す位置がずれます。pinned_prompt は端末の幅を取得し、表示範囲を横にずらして 1 行に収めています。

Windows のコンソールが解釈する文字色の指定 (SGR) は、[Console Virtual Terminal Sequences の Text Formatting](https://learn.microsoft.com/windows/console/console-virtual-terminal-sequences#text-formatting) に一覧があります。  
この一覧には、明るい前景色 `90` から `97` (`90` は明るい黒、つまり灰色) が含まれ、文字を薄くする `2` (faint) は含まれていません。

## 現行の合意内容

ユーザーは、Tab 補完を導入する方針と、補完実装プランを作成して詳細を詰めることを指示しました (2026-10-12 の対話)。  
また、「入力を始めて数文字入力後の補完を想定している」と補足しました (2026-10-12 の対話)。この補足の解釈は [Q-017](#q-017-候補を求める契機) と [Q-020](#q-020-候補を求め始める条件) で確認します。

解決済みの Q により、次の内容が確定しています。

- 補完は prompt と pinned_prompt の両方に提供します ([Q-001](#q-001-補完を提供する-api-の範囲))。
- 候補は、利用側がハンドル単位で登録した補完関数から受け取ります ([Q-002](#q-002-候補の供給方式)、[Q-003](#q-003-補完関数の登録単位))。補完関数は候補とともに置換開始位置を返します ([Q-004](#q-004-置換範囲の決め方))。
- 候補の一覧は表示しません。候補が 1 つに定まる場合だけ、その候補を文字色より薄いグレーで表示し、定まらない場合は何も表示しません ([Q-005](#q-005-複数候補がある場合の操作)、[Q-007](#q-007-pinned_prompt-での候補一覧の表示先))。
- 確定時に空白を自動で付けず ([Q-006](#q-006-候補確定後の区切り文字))、受け付けられない候補は追加する関数が誤りを返して除外します ([Q-010](#q-010-受け付けられない候補の扱い))。
- pinned_prompt では mutex を持ったまま補完関数を呼び、補完関数からの pinned_prompt の API 呼び出しを禁止します ([Q-011](#q-011-pinned_prompt-での補完関数の呼び出しと排他制御))。端末でない場合は補完を行わず、Shift+Tab は対象外です ([Q-012](#q-012-端末でない場合の扱い)、[Q-013](#q-013-shifttab-の扱い))。
- 機能仕様の要件は 1 件とし、カバレッジ 100% の維持とサンプル コマンドへの組み込みを受入条件に含めます ([Q-014](#q-014-機能仕様の要件の粒度)、[Q-015](#q-015-テストの受入基準)、[Q-016](#q-016-サンプル-コマンドへの組み込み))。
- 候補は、文字の入力と削除のたびに、カーソルが行末にあり入力が空でないときに求めます。何文字から候補を返すかは補完関数が判定します ([Q-017](#q-017-候補を求める契機)、[Q-020](#q-020-候補を求め始める条件)、[Q-021](#q-021-候補を求めるカーソル位置の条件))。
- 候補が 1 件の場合だけ、続きの部分を `ESC [ 90 m` の灰色で表示し、端末の右端で切り詰めます。共通部分の表示や、入力済みの部分と前方一致しない候補の表示は行いません ([Q-019](#q-019-候補が複数ある場合の共通部分の扱い)、[Q-022](#q-022-入力済みの部分と前方一致しない候補の扱い)、[Q-023](#q-023-灰色の表示に使う指定)、[Q-024](#q-024-表示幅を超える灰色部分の扱い))。
- 灰色の候補は Tab と行末での → で確定し、確定の直後にも補完関数を呼びます。Enter は灰色の部分を含めずに確定します ([Q-018](#q-018-灰色の候補を確定するキー)、[Q-025](#q-025-enter-を押したときの灰色部分の扱い)、[Q-032](#q-032-確定した直後に候補を求めるか))。
- 公開 API は [Q-027](#q-027-公開-api-の宣言案) の宣言案と契約のとおりとし、登録関数は `cplat_prompt_completion_set` と `cplat_pinned_prompt_completion_set` とします ([Q-028](#q-028-登録関数の名前の形))。
- prompt にも横スクロールを実装し、既存の要件 `CPLAT-PROMPT-FUNC-003` <!-- cplat-req: uuid=bdf48e47-ef70-4fdd-a765-fe08b46f22ac --> を満たします ([Q-026](#q-026-prompt-の入力自体の横スクロールの扱い))。
- 表示幅の計算と表示範囲の調整は `prompt_edit.c` へ移して共通にし、端末サイズの取得は prompt 側に追加して pinned_prompt の処理は残します ([Q-029](#q-029-表示幅の計算と表示範囲の調整の共通化)、[Q-030](#q-030-端末サイズの取得処理の共通化))。
- プロンプト文字列の幅も表示幅の規則で数え、prompt と pinned_prompt の両方で直します ([Q-031](#q-031-プロンプト文字列の表示幅の数え方))。
- `pinned_prompt.c` の固定 FD 呼び出し行 (`CPLAT_FD_SET(STDIN_FILENO, &fds)`) における到達不能な 2 分岐には `GCOVR_EXCL_BR_WITHOUT_HIT: 2/4` を付与し、除外後の集計値 (412/412) を C2 の受入対象としつつ、除外前の計測値 (414/416) と理由も記録します ([Q-033](#q-033-固定-fd-の到達不能分岐と-c2-の受入条件))。
- pinned_prompt の入力待ちタイムアウトやリサイズ通知では、端末サイズの取得後に以前の幅または高さが変わった場合のみ `status_dirty` を設定して再描画し、幅と高さがいずれも変化していない場合は再描画を行いません。また、`pinned_prompt_render_locked` は `status_dirty` のときのみ固定領域の消去、ステータス行、セパレーターを描画して入力行は別に描画し、入力行の編集、カーソル移動、補完の更新だけではセパレーターを再描画しません ([Q-034](#q-034-サイズ不変時の再描画抑止))。

## Q-034 サイズ不変時の再描画抑止

**Status**

解決済み

**Context**

Windows でサンプル コマンド `pinned-prompt` を実行したユーザーから、入力待ち中に画面がちらつく事象が報告されました。  
調査の結果、Windows の入力読み取り (`pinned_prompt_platform_read_char`) は 100 ms ごとの入力待ちタイムアウト (`WAIT_TIMEOUT`) を `-2` (`PINNED_PROMPT_KEY_RESIZE`) として返し、`readline` がそのたびに端末サイズの変更有無を確認せず無条件に `status_dirty = 1` の設定と固定領域の再描画を行っていたことが原因でした。  
この調査結果をユーザーへ説明したところ、「ちらつかないように対策してほしい」と明示的に実装が指示されました。  
さらに、無入力時のちらつき対策を適用した後、ユーザーから「無入力時のちらつきは解消したが、文字を入力するたびにセパレーターがちらつく」との追加報告を受けました。  
調査の結果、`pinned_prompt_render_locked` が文字入力やカーソル移動のたびに固定領域の消去 (`pinned_prompt_clear_control_area` の `\033[J`) とセパレーター描画 (`pinned_prompt_render_separator`) を毎回実行していたこと、および小さい端末で非表示のステータス行がある場合に `status_dirty` が `0` に戻らず残ることが原因でした。

**Question**

入力待ちタイムアウトやリサイズ通知を受けた際に、端末の幅と高さが変化していない場合は再描画を抑止しますか。

**Answer**

回答者: Tetsuo Honda (2026-10-23、対話での明示指示)

調査で原因 (端末サイズが不変でも 100 ms ごとの入力待ちタイムアウトが無条件に再描画されること) を説明した後、ユーザーから「ちらつかないように対策してほしい」と明示的に実装指示がありました。  
これを追加修正の承認として記録します。  
また、その後の「無入力時は解消したが文字入力ごとにセパレーターがちらつく」との追加報告は、継続中のちらつき対策依頼に対する同一要件の継続対応であるため、元の無入力時対策と区別したうえで、ユーザーへ追加要件の再回答を求めずに固定領域と入力行の描画分離を反映します。

**Related**

[Q-001](#q-001-補完を提供する-api-の範囲)、[Q-016](#q-016-サンプル-コマンドへの組み込み)

**Decision**

回答者: Tetsuo Honda (2026-10-23、対話での明示指示)

`pinned_prompt.c` の static 関数 `pinned_prompt_resize_locked` で以前の幅と高さを保存し、端末サイズの取得後に幅または高さのいずれかが変わった場合のみ `status_dirty` を設定して再描画します。  
`readline` の `PINNED_PROMPT_KEY_RESIZE` からは `pinned_prompt_resize_locked` を呼び出し、幅と高さのどちらも変化していない場合は再描画を行いません。入力の編集、別スレッドからの出力、ステータス変更に伴う描画は従来どおり行います。  
無入力時のテストとして、専用 inject アクセサー (`test_pinned_prompt_resize`) とパラメーター テスト `pinnedPromptResizeTest` 4 件を追加し、初期サイズ 80x24 に対して同じサイズ (80x24) なら 0 回、幅または高さが変わる 120x24、80x40、120x40 なら 1 回だけ描画され、その後同じサイズで再確認しても描画が増えないことを `fflush` の呼び出し回数で検証します (版 10 での決定)。

文字入力時のセパレーターちらつきに関する追加報告 (版 11 での継続対応) に対しては、元の無入力時対策に加えて、固定領域無効化の規則を次のとおり定めます。

- `pinned_prompt_render_locked` は `status_dirty` のときのみ、固定領域の消去 (`pinned_prompt_clear_control_area`)、ステータス行、およびセパレーターを描画します。入力行は別に描画します。
- `status_dirty` は固定領域の描画後に、小さい端末で非表示のステータス行があっても `0` にします。
- `pinned_prompt_update_size` は端末の幅または高さの変更時に `status_dirty = 1` を設定するため、端末が大きくなってステータス行が表示可能になれば描画されます。
- `pinned_prompt_cleanup_terminal_locked` で固定領域を消去した場合も `status_dirty = 1` を設定し、再表示可能とします。
- ステータスの内容変更 (`cplat_pinned_prompt_status_set`) および有効・無効の切り替え (`cplat_pinned_prompt_status_enable`) における既存の `status_dirty = 1` 設定は維持します。
- これにより、入力行の編集、カーソル移動、補完更新だけではセパレーターを再描画せず、初期表示、リサイズ、ステータス変更、および消去後の再表示では必要な固定領域を描画します。
- パラメーター テスト `pinnedPromptResizeTest` は、既存のサイズ変化テスト (`redraws_only_when_dimensions_change`) と新しい `typing_preserves_fixed_area` の 2 種類 × 6 条件 (`80x24`、`120x24`、`80x40`、`120x40`、`80x2`、`80x1`) の計 12 件へ拡張します。`typing_preserves_fixed_area` では、文字入力とカーソル移動時に `pinned_prompt_render_separator` の `printf` 呼び出しが増えないこと、ステータス変更後には描画されること、極小端末 (`80x2`、`80x1`) で繰り返し描画しないこと、および消去後の再表示と `pinned_prompt_render_locked` で幅変更を検出したときに再描画されることを確認します。
