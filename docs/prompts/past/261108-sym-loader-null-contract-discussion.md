## 現在の実装と過去の対策記録

`count`、`get`、`reject_count`、`reject_get`、`is_default` はエントリの検査前に内部の解決関数を呼びます。  
`is_failed` はエントリのフィールドを直接参照し、`dispose` は配列と要素を検査せずに参照します。  
一方、`info` は配列要素の NULL を事前検査してエラーを返し、`init` の配列処理は NULL の配列と要素を読み飛ばします。

別案件の最終仕様と BL-013 の追記は、旧 `resolve`、`is_default`、`dispose` を結果コード化したと記録しています。  
しかし、現在の実装は複数先 API であり、旧 `resolve` はなく、`dispose` は `void`、`is_default` は真偽値を直接返します。  
cplat のマージ コミット `1cd66b9b` は複数コールバック先の契約を維持したと記載しています。  
過去の実施記録を削除せず、このマージ後の状態と今回の対処を区別して記録する必要があります。

共通規範は真偽値と成否の分離を示しています。  
一方、値をそのまま返す getter は共通結果コードの適用対象外とも記載しています。  
元の backlog が提案する NULL または 0 の返却だけでは、取得できなかった原因と有効な空の結果が重なる関数があるため、規範と現在の利用方法を踏まえて [Q-001](#q-001-取得系-api-の失敗通知) で契約を決めます。

## 現行の合意内容

- ユーザーは対策の検討を指定しています。最終仕様と実装着手は未承認です。
- 取得系の成否と値は結果コードと出力引数に分け、必須入力または出力が NULL なら `CPLAT_ERR_INVALID_ARGUMENT` を返して出力を変更しません ([Q-001](#q-001-取得系-api-の失敗通知))。
- `dispose` は要素数 0 なら NULL 配列を含めて成功とします。正の要素数で NULL の配列または要素があれば、事前検査で拒否して何も解放しません ([Q-002](#q-002-解放時の不正配列の扱い))。
- `get` の範囲外の添字は `CPLAT_ERR_INVALID_ARGUMENT` を返し、出力を変更しません ([Q-003](#q-003-移譲先の範囲外の添字))。
- 取得・診断で内部の解決処理が失敗した場合は `CPLAT_ERR_UNKNOWN` を返して出力を変更せず、`is_failed` は内部失敗の状態を取得する役割を保ちます ([Q-004](#q-004-内部失敗時の通知))。
- `get_as` を廃止し、関数ポインターは `void *` の一時変数に受けて成功後に型変換します ([Q-005](#q-005-型付き取得マクロの扱い))。
- `base_calc` は取得失敗時に `BASE_ERR_UNKNOWN` を返し、出力を変更しません。取得成功時は従来どおり 0 件なら加算、1 件以上なら先頭を呼びます ([Q-006](#q-006-base_calc-の取得失敗時の扱い))。
- `dispose` で OS のモジュール解放が失敗したときは、失敗した資源を保持し、ほかの資源の解放を続けてエラーを返します。解放待ちの間は取得を拒否し、残ったハンドルは `dispose` で再試行します ([Q-007](#q-007-モジュール解放失敗時の扱い)、[Q-010](#q-010-部分解放後のエントリの利用))。
- `info` は内部失敗時に `CPLAT_ERR_UNKNOWN` を返し、それ以前に出力した表示は取り消しません ([Q-008](#q-008-情報表示時の内部失敗))。
- アンロード時の `dispose` 失敗は当初 `CPLAT_DLLMAIN_INFO_MSG` で通知する方針でしたが、終了関数をアンロード前に呼ぶ方針に変更し、その戻り値で通知します ([Q-009](#q-009-終了処理での解放失敗の通知)、[Q-021](#q-021-windows-での移譲先の寿命)、[Q-022](#q-022-linux-での終了手順))。
- `init` は結果コード化し、解放待ちのエントリを含む配列は設定の読み込み前に `CPLAT_ERR_BUSY` で拒否します ([Q-011](#q-011-部分解放後の再初期化))。
- 初期化・解決途中のモジュール解放失敗も対策し、ハンドルの保持と通知を設計します ([Q-012](#q-012-初期化と解決途中のモジュール解放失敗))。
- モジュールをすべて解放できたエントリはロックを破棄し、解放に失敗したエントリはロックを保持します ([Q-013](#q-013-エントリのロックの寿命))。
- `init` は正の要素数で NULL の配列または要素を事前に拒否し、エントリを変更しません。要素数 0 では NULL 配列を許容します ([Q-014](#q-014-init-の配列引数))。
- `init` は NULL・空のパスと存在しない設定ファイルに対して `CPLAT_SKIPPED` を返し、エントリを変更しません ([Q-015](#q-015-設定が指定されていない場合))。
- `init` は設定ファイルの読み込み・解析失敗をエラーとして通知し、分類できない失敗には `CPLAT_ERR_UNKNOWN` を返します ([Q-016](#q-016-設定ファイルの読み込み失敗))。
- `init` は設定適用中のエントリごとの内部失敗を `CPLAT_ERR_UNKNOWN` で通知し、ほかのエントリの処理を続けます ([Q-017](#q-017-エントリごとの初期化失敗))。
- `override-sample` のロード時に `init` がエラーを返した場合は、既存の診断経路で通知して起動を続けます ([Q-018](#q-018-初期化失敗時のサンプルの動作))。
- `init` 開始後は、対象エントリから以前取得した関数ポインターと診断文字列を使いません ([Q-019](#q-019-再初期化時の取得済みポインターの寿命))。
- Windows の `DllMain` の外で移譲先を解放する終了手順を検討範囲に含め、プロセス終了時は回収を OS に任せます ([Q-020](#q-020-windows-のアンロード時のモジュール解放)、[Q-021](#q-021-windows-での移譲先の寿命))。
- Windows と Linux の明示的アンロード前は、利用側が公開終了関数を呼び、その結果を確認します。プロセス終了時は終了関数の呼び出しを必須にせず、資源の回収を OS に任せます ([Q-021](#q-021-windows-での移譲先の寿命)、[Q-022](#q-022-linux-での終了手順))。
- Windows の明示的アンロード時に終了関数の未実行を検出できた場合は診断を出します。Linux では正常なプロセス終了と区別できないため通知しません ([Q-023](#q-023-終了関数を呼ばないアンロードの通知))。

## 明確化のための確認項目

### Q-001 取得系 API の失敗通知

**Status**

解決済み

**Question**

エントリが NULL の場合に失敗を区別できるよう、対象の取得系 API の戻り値と出力引数を見直しますか。

**Context**

現在の `count` と `reject_count` は `size_t`、`get` はポインター、`is_default` と `is_failed` は 0 または 1 を直接返します。  
NULL に対して単に 0 や NULL を返すと、移譲先が 0 件などの通常結果と区別できません。  
`reject_get` はすでに結果コードを返すため、エントリの NULL も不正な引数として扱う案です。

案 A では、たとえば `int cplat_sym_loader_count(cplat_sym_loader_entry *entry, size_t *count_out)` のように値を出力引数へ移し、成否を結果コードで返します。

### Q-021 Windows での移譲先の寿命

**Status**

解決済み

**Question**

Windows で `libbase` をプロセス終了前に明示的にアンロードする利用を、今回サポートしますか。

**Context**

[Q-020](#q-020-windows-のアンロード時のモジュール解放) では `DllMain` の外で解放する方法に加え、プロセス終了まで解放しない方法も検討することになりました。  
[Microsoft の DllMain の説明](https://learn.microsoft.com/en-us/windows/win32/dlls/dllmain) は、プロセス終了時には DLL が資源を解放せず OS に回収させるよう示しています。  
一方、プロセスが継続する明示的アンロードでは、OS に回収を任せてもその時点ではプロセス全体は終了せず、残ったモジュール参照や動的メモリは直ちには回収されません。  
再ロードを繰り返す場合は残資源が増えるおそれがあり、残ったモジュールやその依存関係が後のアンロードに影響することもあります。  
サンプルの `liboverride` は `libbase` にリンクし、`base_console_output` も呼び出します。

`dispose` 以外にも、解決を伴う取得・情報表示は `LoadLibrary` を呼び、設定を入れ替える `init` は `FreeLibrary` を呼ぶ場合があります。  
[Microsoft の DLL 開発指針](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-best-practices) は `DllMain` 内からの `LoadLibrary` も避けるよう示しているため、これらの操作もローダー ロック下では実行しない利用条件が必要です。  
現在のサンプルの `onLoad` は、未解決のエントリへ設定を読み込む初回の `init` です。

案 A は、明示的アンロード前に利用側が `DllMain` の外で `libbase` の公開終了関数を呼び、移譲先と管理資源を解放します。  
終了関数の成功後は、アンロード前に `base_calc` や情報表示を再び呼びません。  
失敗した場合は [Q-007](#q-007-モジュール解放失敗時の扱い) に従い資源を保持し、利用側はアンロードせず再試行できます。  
プロセス終了時は終了関数を必須にせず、`DllMain` 内からの解放も行いません。  
利用側が終了関数を呼ばずに明示的アンロードを試みる場合の扱いは、別途確認が必要です。  
この場合、[Q-009](#q-009-終了処理での解放失敗の通知) で想定した `onUnload` 内の解放失敗の通知に代わり、終了関数の戻り値で利用側に失敗を通知します。

案 B は、`libbase` と移譲先をプロセス終了まで保持し、明示的アンロードや再ロードをサポートしません。  
この場合は公開終了関数を要求せず、プロセス終了までモジュール参照と管理資源を保持します。  
明示的アンロードを試みた場合の動作は保証せず、依存関係によって `libbase` が実際にはアンロードされない場合もあります。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) 明示的アンロードをサポートし、事前に `DllMain` 外で公開終了関数を呼ぶ。
- [ ] B: プロセス終了まで保持し、明示的アンロード・再ロードをサポートしない。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)
