# ファイル入出力 API の選定基準

固定レコード長バイナリ ファイルや構造体配列の入出力で、`cplat` の `stdio` ラッパー API とメモリ マップド ファイル API のどちらを使うかを、実測に基づいて判断するための基準をまとめます。

cplat が公開する API 全体の一覧は [cplat API チート シート](api-cheatsheet.md) を参照してください。

測定方法は [ベンチマークの測定方法](https://github.com/Hondarer/app_cplat/blob/main/prod/src/cmd/bench-io/benchmark-method.md) を参照してください。  
本書の表は `bench-io` の出力から転記したものです。CSV そのものは実行環境ごとに値が変わるため、リポジトリでは管理していません。

## 測定条件

| 項目 | Linux | Windows |
|------|-------|---------|
| 環境 | WSL2、Intel Xeon Gold 6254 3.10 GHz | Intel64 Family 6 Model 85 Stepping 7 |
| ファイル システム | ext4 | NTFS |
| ページ キャッシュ | warm | warm |
| レコード サイズ | 64 バイト | 64 バイト |
| ファイル サイズ | 4 KB ～ 1 GB | 4 KB ～ 1 GB |

Table: bench-io の測定環境と実行条件

本書の数値はすべて 1 レコードあたりの所要時間 (ナノ秒) の中央値で、表中は **Linux / Windows** の順に併記しています。  
値は環境に強く依存するため、傾向と桁を読み取る目的で使用し、絶対値をそのまま他環境へ持ち込まないでください。

Windows の測定値には、ウイルス対策ソフトウェアによるファイル アクセスの監視が含まれる可能性があります。  
`stdio` 側の値が Linux に対して極端に大きいのは、この影響を含んでいるためと考えられます。

## 結論の要約

1. アタッチを保持したまま繰り返しアクセスできるなら、mmap がほぼすべてのパターンで優位です。この形態の性能は Linux と Windows でほぼ同一になります。
2. 1 回開いて 1 回通すだけの逐次アクセスでは、mmap の優位はなく、`stdio` のブロック単位読み書きが最良です。
3. ランダム アクセス、特に read-modify-write では mmap が大幅に高速です。
4. 単発参照や短命なオープンが支配的な用途では `stdio` が優位です。
5. 書き込みをディスクへ確実に反映する要件があると、mmap の同期コストが大幅に増加します。
6. **オープンやアタッチの固定コストは Windows が Linux の 20 ～ 30 倍です。** ファイルを頻繁に開閉する設計は、Windows で不利の度合いが大幅に増します。
7. **ファイルが数百 MB を超えると、アタッチを保持しない mmap は急速に不利になります。** 1 GB のランダム アクセスでは Linux で `stdio` に逆転されます。

## 固定コスト (ファイル サイズに依存しない)

| 操作 | Linux | Windows | 比 |
|------|-------|---------|-----|
| `cplat_fopen` → `cplat_fclose` | 1.8 μs | 52 ～ 56 μs | 約 30 倍 |
| `cplat_mmap_attach` → `cplat_mmap_detach` | 6.2 ～ 8.9 μs | 134 ～ 149 μs | 約 20 倍 |

Table: オープンとアタッチの固定コスト

アタッチは `fopen` の 2.6 ～ 3.6 倍のコストがかかります。  
`fopen` はファイル サイズによらず一定ですが、アタッチはマップするサイズに応じてわずかに増加します  
(Linux では 4 KB の 6.2 μs に対し 1 GB で 8.9 μs)。  
いずれにせよ 1 回のアタッチでどれだけの処理をこなすかが選定の分かれ目になります。

## パターン別の比較

次の表はすべて **Linux / Windows** の順で、1 レコードあたりの所要時間 (ns) を示します。

### 逐次読み取り (seq-read)

| ファイル サイズ | `stdio-rec` | `stdio-blk` | `mmap-each` | `mmap-once` |
|------|------|------|------|------|
| 4 KB | 53.0 / 1192.1 | 40.6 / 1102.4 | 177.3 / 2327.0 | 0.6 / 0.7 |
| 64 KB | 20.5 / 160.2 | 6.0 / 76.3 | 18.6 / 182.4 | 0.8 / 0.8 |
| 1 MB | 20.5 / 93.1 | 5.2 / 12.6 | 6.9 / 46.6 | 1.2 / 0.8 |
| 16 MB | 24.0 / 98.7 | 7.6 / 14.4 | 8.3 / 39.1 | 2.8 / 2.5 |
| 256 MB | 26.8 / 102.5 | 10.5 / 17.3 | 10.9 / 40.1 | 5.6 / 4.4 |
| 1 GB | 26.1 / 100.6 | 9.9 / 18.6 | 11.3 / 44.7 | 5.3 / 4.7 |

Table: 逐次読み取りの 1 レコードあたり所要時間 (ns、Linux / Windows)

**`mmap-once` は両 OS でほぼ同一の値になります。**

アタッチを保持したあとの処理はメモリ アクセスだけであり、システム コールを伴わないためです。  
ファイル入出力の性能を OS 差の影響から切り離したい場合、この形態がもっとも安定します。

アタッチを毎回行う `mmap-each` は、どちらの OS でも `stdio-blk` を上回りません。  
一方 Windows では `mmap-each` が `stdio-rec` を 1 MB 以上で逆転します (46.6 対 93.1)。  
Windows の `stdio` はレコード単位の呼び出しコストが大きく、mmap のアタッチ コストを償却できる規模になると不利が逆転するためです。

レコード単位で読む `stdio-rec` はブロック単位の `stdio-blk` に対して、Linux で 2 ～ 4 倍、**Windows では 6 ～ 8 倍** 遅くなります。  
`stdio` を使う場合、逐次アクセスではブロック単位でまとめて読み書きしてください。この指針は Windows でより重要です。

### ランダム読み取り (rand-read)

| ファイル サイズ | `stdio-rec` | `mmap-each` | `mmap-once` |
|------|------|------|------|
| 4 KB | 217.6 / 5363.5 | 199.1 / 2323.1 | 0.8 / 0.8 |
| 64 KB | 493.4 / 5012.5 | 20.0 / 182.4 | 0.9 / 0.8 |
| 1 MB | 564.0 / 4890.4 | 7.9 / 49.4 | 1.7 / 1.2 |
| 16 MB | 833.6 / 7392.9 | 26.8 / 156.4 | 8.4 / 4.3 |
| 256 MB | 1138.3 / 7515.0 | 332.8 / 1579.3 | 28.9 / 12.1 |
| 1 GB | 1247.5 / 8102.4 | 1476.5 / 2441.4 | 34.5 / 16.3 |

Table: ランダム読み取りの 1 レコードあたり所要時間 (ns、Linux / Windows)

`stdio` はレコードごとに `cplat_fseek` を伴うため、CRT の先読みバッファーが機能しません。  
mmap はページ フォールト以外のオーバーヘッドがなく、`mmap-once` で Linux は 7 ～ 40 倍、**Windows は 250 ～ 6000 倍** 高速です。  
アタッチを毎回行う `mmap-each` は、64 KB から 256 MB までの範囲ではどちらの OS でも `stdio` を大きく上回ります。

**ただし 1 GB では Linux で逆転し、`mmap-each` (1476.5) が `stdio-rec` (1247.5) より遅くなります。**

256 MB から 1 GB にかけて `mmap-each` が 4.4 倍に悪化する一方、`stdio-rec` はほぼ横ばいです。  
アタッチのたびに巨大なマッピングを構築し、ランダムに触れたページのフォールトをやり直すコストが、マップ サイズに応じて増大するためと考えられます。  
Windows でも同じ悪化傾向 (1579.3 から 2441.4) が見られますが、`stdio` 側がさらに遅いため逆転には至っていません。

### ランダム更新 (rand-update)

| ファイル サイズ | `stdio-rec` | `mmap-each` | `mmap-once` |
|------|------|------|------|
| 4 KB | 1351.0 / 206054.7 | 225.3 / 2323.1 | 1.1 / 1.6 |
| 64 KB | 1333.2 / 30517.6 | 36.9 / 190.0 | 1.3 / 1.7 |
| 1 MB | 1413.9 / 10498.0 | 22.9 / 57.8 | 2.1 / 2.3 |
| 16 MB | 1738.6 / 13824.5 | 97.5 / 190.0 | 9.4 / 5.4 |
| 256 MB | 2094.6 / 14297.5 | 1144.2 / 2147.7 | 30.5 / 12.8 |
| 1 GB | 2264.9 / 14068.6 | 2742.4 / 3097.5 | 36.1 / 17.2 |

Table: ランダム更新の 1 レコードあたり所要時間 (ns、Linux / Windows)

`stdio` の read-modify-write は突出して遅く、`mmap-once` に対して Linux で 75 ～ 1250 倍、**Windows では 1100 ～ 130000 倍** の差がつきます。  
同一ストリームで読み取りと書き込みを交互に行うと、C 標準の規定により方向を切り替えるたびにバッファーの掃き出しと位置合わせが発生するためです。

**構造体配列に対するランダムな読み書きが処理の中心である場合、`stdio` は選択肢になりません。**

この結論は両 OS で共通し、Windows ではさらに顕著です。  
ただしランダム読み取りと同様に、1 GB では Linux の `mmap-each` (2742.4) が `stdio-rec` (2264.9) より遅くなります。  
**アタッチを保持できない場合、mmap の優位は 256 MB 付近を境に失われます。**

### 逐次書き込み (seq-write)

| ファイル サイズ | `stdio-rec` | `stdio-blk` | `mmap-each` | `mmap-once` |
|------|------|------|------|------|
| 4 KB | 63.2 / 31463.6 | 48.0 / 30517.6 | 214.6 / 2265.9 | 2.5 / 2.5 |
| 64 KB | 27.1 / 9292.6 | 11.2 / 10726.9 | 37.1 / 178.8 | 3.2 / 3.3 |
| 1 MB | 26.7 / 1340.9 | 10.1 / 640.9 | 24.4 / 42.9 | 3.4 / 3.2 |
| 16 MB | 32.4 / 260.8 | 14.7 / 117.3 | 26.9 / 38.1 | 5.0 / 4.1 |
| 256 MB | 40.3 / 141.6 | 24.8 / 32.6 | 32.1 / 40.1 | 8.6 / 7.5 |
| 1 GB | 39.5 / 137.9 | 23.9 / 29.3 | 30.9 / 47.4 | 8.5 / 7.7 |

Table: 逐次書き込みの 1 レコードあたり所要時間 (ns、Linux / Windows)

Linux では逐次読み取りと同じ傾向です。

**Windows では小さいファイルへの書き込みが際立って高コストです。**

4 KB で `stdio-blk` が 30517.6 ns/レコードに達します。64 レコードあたり約 2 ms であり、NTFS のメタデータ更新とファイル作成の処理が支配的になっています。  
Windows で小さなファイルを頻繁に書き換える設計は、API の選択にかかわらず避けてください。

### 単発参照 (point-lookup) とオープンのみ (open-close)

| API | point-lookup | open-close |
|-----|------|------|
| `stdio-rec` | 3.2 / 76.3 μs | 1.8 / 53.4 μs |
| `mmap-each` | 18.0 / 156.5 μs | 6.6 / 141.1 μs |
| `mmap-once` | 6 / 6 ns | (対象外) |

Table: 単発参照とオープンのみの所要時間 (Linux / Windows、ファイル サイズによらずほぼ一定)

ファイルを開いて 1 レコード読んで閉じる用途では `stdio` が Linux で 4 ～ 6 倍、Windows で約 2 倍高速です。  
mmap はアタッチの固定コストを 1 レコードで償却できません。

## 耐久性を要求した場合

| ファイル サイズ | `mmap-once` | `mmap-once+sync` | `stdio-blk` | `stdio-blk+sync` |
|------|------|------|------|------|
| 4 KB | 2.5 / 2.5 | 25310.9 / 5371.1 | 48.0 / 30517.6 | 48.8 / 31951.9 |
| 64 KB | 3.2 / 3.3 | 2151.5 / 387.7 | 11.2 / 10726.9 | 11.4 / 11215.2 |
| 1 MB | 3.4 / 3.2 | 228.6 / 93.1 | 10.1 / 640.9 | 10.3 / 701.0 |
| 16 MB | 5.0 / 4.1 | 134.6 / 81.9 | 14.7 / 117.3 | 14.6 / 115.4 |
| 256 MB | 8.6 / 7.5 | 73.7 / 76.3 | 24.8 / 32.6 | 25.1 / 33.6 |
| 1 GB | 8.5 / 7.7 | 70.3 / 75.5 | 23.9 / 29.3 | 24.3 / 28.0 |

Table: 逐次書き込みでディスクへの反映を要求した場合の 1 レコードあたり所要時間 (ns、Linux / Windows)

`cplat_mmap_flush` のコストは、小さいファイルほど不利になります。  
`msync` や `FlushViewOfFile` の呼び出しコストとディスクへの書き戻し待ちを、少数のレコードで割ることになるためです。

**Windows の `cplat_mmap_flush` は、小さいファイルでは Linux よりむしろ低コストです** (4 KB で 5371 対 18816、64 KB で 388 対 1813)。  
Windows では `FlushViewOfFile` に加えて `FlushFileBuffers` を呼び出すため Linux より高コストになると想定していましたが、実測は逆でした。

**`stdio-blk+sync` と `stdio-blk` にはどちらの OS でもほとんど差がありません。**

これは `cplat_fflush` が CRT のバッファーを OS へ渡すだけで、ディスクへの書き戻しまでは待たないためです。  
両者は耐久性の水準が異なるため、**`+sync` 同士の数値を直接比較しないでください。**  
`stdio` で mmap と同等の耐久性を得るには、`fflush` に加えて `fsync` 相当の処理が必要ですが、`cplat` にはそのラッパーがありません。

## 判断手順

上から順に評価し、最初に当てはまった項目に従ってください。  
判断は両 OS で共通です。

1. **ネットワーク ファイル システム上のファイルか**  
   → `stdio` を使用します。`cplat_mmap_attach` の `@warning` のとおり、mmap はローカル ファイル システム専用です。

2. **ファイル サイズがアドレス空間に収まらないか、実行時まで確定しないか**  
   → `stdio` を使用します。現在の `cplat_mmap` は部分範囲マップに対応しておらず、ファイル全体を一度にマップします。

3. **追記によってファイルを伸長するか**  
   → `stdio` を使用します。既存ファイルを開いた時点のサイズがマップ サイズに固定されるため、mmap では追記できません。

4. **1 回のオープンで扱うレコード数が数十未満か (単発参照が中心か)**  
   → `stdio` を使用します。アタッチの固定コスト (Linux 約 6.6 μs、Windows 約 141 μs) を償却できません。

5. **ランダム アクセス、特に read-modify-write が処理の中心か**  
   → mmap を使用します。`stdio` との差は 1 桁から 5 桁に達します。  
   ただしアタッチを保持できず、かつファイルが数百 MB を超える場合は、mmap の優位が失われます (下の項目 6 を参照)。  
   この条件では `stdio` のブロック単位読み書きを検討してください。

6. **同じファイルへ繰り返しアクセスし、ハンドルを保持できるか**  
   → mmap を使用します。アタッチを保持すればすべてのパターンで優位であり、性能の OS 差もほぼ消えます。  
   1 GB でも `mmap-once` の値は 256 MB とほぼ変わらず、サイズの影響をほとんど受けません。  
   逆にアタッチを保持できない場合、ランダム アクセスでの mmap の優位は 256 MB を境に急速に失われ、1 GB では Linux で `stdio` に逆転されます。**巨大ファイルを mmap で扱うなら、アタッチの保持が前提です。**

7. **1 回開いて全体を 1 度だけ通す逐次処理か**  
   → `stdio` のブロック単位読み書き (`cplat_fread` / `cplat_fwrite` を 64 KB 程度でまとめる) を使用します。  
   mmap にしても同等以上にはならず、実装は複雑になります。

8. **上のいずれにも当てはまらない**  
   → `stdio` のブロック単位読み書きを既定とします。性能が問題になった時点で本書の表と照らして mmap への切り替えを検討してください。

## プロセス間共有が必要な場合

複数プロセスから同一ファイルを読み書きする場合も、I/O API はアクセス パターンとファイル サイズに基づいて選びます。  
排他制御が必要な場合は、I/O API とは独立して `sync` のプロセス横断ミューテックスまたはプロセス横断読み書きロックを使用します。

共有モードと排他制御の関係は、[コーディング規範のプラットフォーム差異の共通契約](coding-guideline.md#プラットフォーム差異の共通契約) を参照してください。  
`stdio` と mmap のどちらもプロセス間の排他機構を内包しません。  
同期ハンドルの識別子、所有権、寿命は呼び出し側で管理してください。

## OS による差

実測から確認できた差は次のとおりです。

- **固定コストの差が最大の相違点です。** オープンとアタッチはいずれも Windows が Linux の 20 ～ 30 倍かかります。ファイルの開閉頻度を下げる設計は、両 OS で有効ですが Windows で効果が大きくなります。
- **`mmap-once` の性能は OS にほとんど依存しません。** アタッチ後の処理はメモリ アクセスのみであり、両 OS の値は誤差の範囲で一致します。
- **`stdio` の性能は OS 差が大きく出ます。** Windows は Linux に対して逐次で 4 ～ 5 倍、ランダムで 8 倍程度遅くなります。Windows の測定値にはウイルス対策ソフトウェアの監視が含まれる可能性があるため、この差の一部は環境要因です。
- **小さいファイルへの書き込みは Windows で特に高コストです。** 4 KB のファイルへの逐次書き込みは Linux の約 600 倍かかります。
- **`cplat_mmap_flush` は小さいファイルで Windows のほうが低コストです。** 想定と逆の結果でした。大きいファイル (256 MB) ではほぼ同等になります。

## 現在の cplat_mmap API の制限

判断手順で `stdio` を選ぶ根拠になっている制限です。将来 API が拡張されれば基準も変わります。

- 既存ファイルを開くと、その時点のファイル サイズが固定のマップ サイズになり、追記による伸長ができません。
- 部分範囲マップ (オフセットと長さの指定) に対応していません。
- マップ サイズが 0 の場合はアタッチに失敗します。
- ネットワーク ファイル システム上ではプロセス間の一貫性が保証されません。

## 測定していない条件

次の条件は測定範囲外です。結論を適用する際は注意してください。

- ページ キャッシュをクリアした状態 (cold)。WSL2 では測定できないため、ネイティブ Linux での実施が必要
- 1 GB を超えるファイル。1 GB で確認された `mmap-each` の悪化がさらに進むかは未確認
- 複数プロセスからの同時アクセス下での性能
- HDD やネットワーク ストレージなど、ext4 と NTFS 以外のストレージ
- 64 バイト以外のレコード サイズ
- ウイルス対策ソフトウェアを無効化した状態の Windows
