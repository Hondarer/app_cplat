# 条件付きファイル コピー関数の設計

cplat を利用して、Linux/GCC と Windows/MSVC の双方で動作するファイル コピー関数を新規に設けるための設計プランです。

実装のサンプルは [file_copy_sample.c](file_copy_sample.c) にあります。  
本書はコードを掲載せず、仕様、処理の流れ、判断の根拠、制限事項だけを扱います。

本書と `file_copy_sample.c` は `prompt/` 配下の作業用ファイルであり、Git の管理対象外です。  
配置先の app が決まった段階で、本書を `app/<name>/docs/` へ、実装を `app/<name>/prod/` へ移します。

## 目的

同じサイズを保つ既存ファイルを、コピー元のほうが新しいときだけ上書きして最新化します。

想定するのは、固定長のバイナリ ファイルや構造体配列のように、サイズが設計時に決まっている対象です。  
サイズの一致を事前条件にすることで、コピー先のファイル実体を保ったまま先頭から上書きでき、ファイル実体に結び付いた外部の排他機構を壊さずに済みます。

## 前提条件

呼び出し側は、次の条件を満たした状態で本関数を呼び出します。

- コピー元とコピー先の双方について、他プロセスによる更新が外部の機構で排除されている
- コピー先がすでに存在し、コピー元と同じサイズを持つ

本関数は排他制御を行いません。  
排他の手段は呼び出し側の選択に委ねますが、`cplat` の `sync.h` が提供する `cplat_interprocess_lock` と `cplat_interprocess_rwlock` を利用できます。

## サンプル実装の所在

[file_copy_sample.c](file_copy_sample.c) は単一の翻訳単位で、次の順に並んでいます。

1. 結果コードの `#define`
2. 内部定数 (転送バッファーのサイズ)
3. 公開関数のプロトタイプと Doxygen コメント
4. 内部の `static` 関数 (種別判定、ファイル情報の取得、転送、本体)
5. 公開関数の定義

app へ移す際は、項目 1 と項目 3 を `prod/include/<lib>/` の公開ヘッダーへ移し、残りを `prod/libsrc/<lib>/` へ配置します。  
あわせて `sample_` と `SAMPLE_` の接頭辞を、配置先の lib 名へ置き換えます。

## API 仕様

関数名は [共通コーディング規範](../../../general/docs/coding-guideline.md) の命名規則に従い、`<lib>_<カテゴリ名詞>_<動詞>` の順で並べます。  
配置先の app が未確定のため、規範の記述例と同じ `sample_` をプレースホルダーとして使います。

`int sample_file_copy_if_newer(const char *from_path, const char *to_path, cplat_error *detail_out);`

| 引数 | 方向 | 意味 |
|------|------|------|
| `from_path` | `[in]` | コピー元のパス (UTF-8)。NULL を渡してはなりません |
| `to_path` | `[in]` | コピー先のパス (UTF-8)。NULL を渡してはなりません |
| `detail_out` | `[out]` | エラー詳細の格納先。NULL を許容します |

Table: sample_file_copy_if_newer 関数の引数仕様

`detail_out` の扱いは cplat の既存 API と同じです。  
NULL を指定した場合は詳細を返さず、NULL 以外を指定した場合は成功時に空の値を格納します。

## 結果コード

戻り値は app ごとの共通結果コード群です。  
成功は 0 のみ、エラーは負値、エラーではない省略は正値とし、cplat の `CPLAT_SKIPPED` と同じ考え方を採ります。

| コード | 値 | 意味 |
|--------|-----|------|
| `SAMPLE_OK` | 0 | コピーを実行しました |
| `SAMPLE_SKIPPED` | 1 | コピー元が新しくないため、コピーを省略しました |
| `SAMPLE_ERR` | -1 | 分類済みコードに該当しない、その他のエラーです |
| `SAMPLE_ERR_INVALID_ARGUMENT` | -2 | 引数が不正です |
| `SAMPLE_ERR_NOT_FOUND` | -3 | いずれかが通常ファイルとして存在しません |
| `SAMPLE_ERR_SIZE_MISMATCH` | -4 | ファイル サイズが一致しません |
| `SAMPLE_ERR_OUT_OF_MEMORY` | -5 | 転送バッファーを確保できません |

Table: sample_file_copy_if_newer 関数の結果コード一覧

`SAMPLE_SKIPPED` は失敗ではありません。  
呼び出し側は判定を `!= SAMPLE_OK` ではなく、目的に応じてコード名との比較で行ってください。

コピー先がディレクトリだった場合も `SAMPLE_ERR_NOT_FOUND` を返します。  
「通常ファイルとして存在しない」ことを、存在しない場合と同じ分類にまとめているためです。

## 処理手順

1. `from_path` と `to_path` の NULL を検査します
2. `cplat_stat()` でコピー元とコピー先のファイル情報を取得します。  
   取得に失敗した場合、`cplat_error_is()` が `CPLAT_CAUSE_NOT_FOUND` を示せば `SAMPLE_ERR_NOT_FOUND`、それ以外は `SAMPLE_ERR` を返します
3. 双方が通常ファイルであることを確認します
4. `st_size` を `int64_t` へそろえて比較し、一致しなければ `SAMPLE_ERR_SIZE_MISMATCH` を返します
5. `difftime()` で `st_mtime` の差を求め、コピー元が新しくなければ `SAMPLE_SKIPPED` を返します
6. 転送バッファーを確保し、コピー元を読み取りアクセスで、コピー先を書き込みアクセスで開きます
7. 読み取りと書き込みを繰り返し、転送量が事前に確認したサイズと一致することを確認します
8. コピー先を永続記憶装置へ反映し、双方を閉じ、バッファーを解放します

手順 1 から手順 5 までは資源を確保していないため、早期の `return` で復帰します。  
手順 6 以降は資源解放の `goto` で後始末を 1 箇所へ集約します。  
これは共通コーディング規範が `goto` を限定的に許容している唯一の用途です。

`cplat_file_read()` は終端以外でも要求より少ない量を返すため、読み取り量が 0 になるまで繰り返します。  
`EINTR` は cplat の共通契約により Linux 側で吸収されるため、呼び出し側での再試行は不要です。

## 設計判断の根拠

### OS のコピー API を採らない理由

`CopyFileW` などの OS が用意するコピー API で転送ループを省けないかを検討しましたが、採用しません。

第一に、簡便になるのは Windows だけです。  
Linux に `CopyFileW` の等価物はありません。  
`copy_file_range(2)` は要求より少ない転送量を返すためループが必要で、カーネル 4.5 未満と、5.3 未満での異なるファイル システム間のコピーは `ENOSYS` または `EXDEV` になります。  
フォールバックの読み書きループを併存させることになり、Linux 側の実装量はむしろ増えます。  
その結果、分岐した 2 系統をそれぞれ検証する必要が生じます。

第二に、共有モードが外部の排他と衝突しうる点が最大の懸念です。  
`CopyFileW` はコピー先を他プロセスと共有しない形で開きます。  
前提の排他がファイル ハンドルの保持で実現されている場合、Windows 側だけが共有違反で失敗します。  
cplat の `cplat_file_open()` は `FILE_SHARE_READ`、`FILE_SHARE_WRITE`、`FILE_SHARE_DELETE` を指定して他プロセスの読み取り、書き込み、削除を妨げない方針を明記しており、`CopyFileW` はこの共通契約から外れます。

第三に、抽象化の層から外れます。  
`win32.h` に `CopyFileU` ラッパーはなく、リポジトリ内に `CopyFile` の使用例もありません。  
app から直接 `CopyFileW` を呼び出すと、Win32 へのアクセスを cplat へ集約する現在の構成から外れ、UTF-8 から UTF-16 への変換も app 側で持つことになります。

第四に、削減できる範囲が限定的です。  
存在確認、サイズの一致、更新日時の比較は `CopyFileW` では判定できないため、`cplat_stat()` の呼び出しは残ります。  
後述の Coverity への対応も変わらず、省けるのは転送ループだけです。

### in-place 上書きを選ぶ理由

コピー先を切り詰めず、一時ファイルと `rename` も使わず、既存のファイル実体へ先頭から上書きします。

コピー先のファイル実体を保つためです。  
cplat はファイル実体の同一性を `cplat_file_id` の `volume` と `index` で表し、リネームでは値が変化しないと定めています。  
一時ファイルを `rename` で置き換えると実体が入れ替わるため、外部の排他がファイル実体に結び付いている場合に排他が破綻します。

サイズの一致を事前条件にしているため、先頭からの上書きで全長が置き換わります。  
切り詰めが不要であることも、この方式を選べる理由です。

### mmap を使わない理由

[ファイル入出力 API の選定基準](../fileio-api-selection-guideline.md) の判断手順のうち、「1 回開いて全体を 1 度だけ通す逐次処理」が本関数に該当します。  
この形態ではブロック単位の読み書きが最良であり、mmap にしても同等以上にはならず実装だけが複雑になります。

転送バッファーは 64 KB とします。  
同資料が逐次アクセスでブロック単位にまとめる指針を示しており、その規模に合わせています。

## 制限事項

### 中断時にコピー先が不定になる

上書きの途中で失敗すると、コピー先は新旧が混在した不定の状態になります。  
この状態から自動的に回復するため、失敗時にコピー先の最終更新日時をコピー開始前の値へ戻します。  
日時を戻すと、次回の呼び出しで再びコピー元のほうが新しくなり、コピーが再試行されて壊れた内容が上書きされます。

戻す値は事前条件の判定で取得済みのため、追加の取得は不要です。  
回復は `cplat_file_set_path_modified_timestamp()` で行います。

回復は最善努力です。  
日時を戻す前にプロセスが停止した場合は回復できず、壊れた内容が省略判定で残り続けます。  
また、日時を戻した直後のコピー先は、内容が壊れているにもかかわらず日時だけが正常に見えます。  
コピー先の最終更新日時を信頼する利用者が他にいる場合は、この点を確認してください。

失敗時にコピー先を 0 バイトへ切り詰める案は採りません。  
サイズの不一致が永続し、以後の呼び出しがすべて `SAMPLE_ERR_SIZE_MISMATCH` で失敗するため、回復の機会を永久に失うためです。

### 更新日時の粒度はファイル システムに依存する

日時の比較には `cplat_file_get_path_modified_timestamp()` を使い、サブ秒まで見ます。  
`cplat_stat()` の `st_mtime` は秒精度のため、比較には使いません。

ただし記録できる粒度はファイル システムに依存します。  
Windows の NTFS は 100 ナノ秒、FAT は 2 秒です。  
粒度より短い間隔で更新されたコピー元は、同値と判定されて省略されます。

## Coverity 対応

`cplat_stat()` による確認と、その後のオープンとの間には、検査から使用までの時間差があります。  
Coverity はこの形を TOCTOU として検出します。

本関数は外部の排他を前提としており、この区間でファイル実体は入れ替わりません。  
実装で解消するのではなく、注釈で抑制します。

抑制の機構は `#pragma` ではありません。  
Coverity にソース内の `#pragma` で欠陥を抑制する機構はなく、`#pragma coverity compliance` は MISRA のコンプライアンス用であって欠陥の抑制には使えません。  
正しい機構は、欠陥が報告される行の直前に置く `coverity[<チェッカー名>]` 形式のコード注釈コメントです。  
`file_copy_sample.c` では、2 箇所のオープンの直前にこの注釈と抑制の理由を併記しています。

本リポジトリにコード注釈の前例はありません。  
既存の Coverity 関連は `prod/coverity.mk` によるビルド統合だけで、ソース内の抑制は MSVC 警告に対する `#pragma warning(suppress : 4996)` にとどまります。  
本設計が初例になるため、抑制の理由をコメントで必ず併記する運用とします。

チェッカー名の表記が `TOCTOU` と `toctou` のどちらであるかは、実際の解析結果の出力に合わせて確定します。

抑制の箇所を減らす代替案として、サイズと更新日時の取得をハンドル経由へ寄せる方法があります。  
`cplat_file_get_size()` と `cplat_file_get_modified_timestamp()` はいずれもハンドルを受け取るため、オープンしてから取得すれば検査と使用の時間差が消えます。  
ただし通常ファイルかどうかの判定は、パスを受け取る `cplat_stat()` に依存します。  
この判定をオープンの成否で代替できるかは確認していません。Linux の `open()` は読み取り専用であればディレクトリも開けるため、そのままでは代替になりません。

## プラットフォーム差異

[C/C++ プラットフォーム抽象化ガイドライン](../platform-abstraction-guideline.md) に従い、`_WIN32` や `_MSC_VER` を直接使わず `PLATFORM_LINUX` と `PLATFORM_WINDOWS` で分岐します。  
分岐の順は Linux、Windows の順です。

| 項目 | Linux | Windows |
|------|-------|---------|
| `cplat_file_stat_t` の実体 | `struct stat` | `struct _stat64` |
| `st_size` の型 | `off_t` | `__int64` |

Table: ファイル状態取得におけるプラットフォーム差異

`st_size` は型が異なるため、`int64_t` へそろえて比較します。  
`long` は LP64 と LLP64 で幅が変わるため使いません。

本関数に残る OS 依存はこの 1 点だけです。  
通常ファイルの判定と最終更新日時の取得および設定は、cplat 側の API が差異を吸収します。  
後述の「OS 差異を吸収する cplat の API」を参照してください。

## OS 差異を吸収する cplat の API

本関数は、通常ファイルの判定と最終更新日時の扱いを cplat の API に委ねます。  
利用側に OS 差異が漏れないのは、次の API が差異を内部で吸収するためです。

| ヘッダー | API | 役割 |
|----------|-----|------|
| `cplat/crt/sys/stat.h` | `cplat_file_stat_is_regular` | 通常ファイルかどうかを OS 差異なしに判定します |
| `cplat/crt/file.h` | `cplat_file_get_modified_timestamp` | 開いているファイルの最終更新日時をサブ秒で取得します |
| `cplat/crt/file.h` | `cplat_file_set_modified_timestamp` | 開いているファイルの最終更新日時を設定します |
| `cplat/crt/file.h` | `cplat_file_get_path_modified_timestamp` | パスが指すファイルの最終更新日時をサブ秒で取得します |
| `cplat/crt/file.h` | `cplat_file_set_path_modified_timestamp` | パスが指すファイルの最終更新日時を設定します |

Table: ファイル コピー処理で OS 差異を吸収する cplat API

### 通常ファイルの判定

`cplat_stat()` が返す `cplat_file_stat_t` は、Linux の `struct stat` と Windows の `struct _stat64` の別名であり、OS の構造体をそのまま公開しています。  
`st_mode` を利用側で解釈すると、`S_ISREG()` と `_S_IFMT` の分岐を両 OS 分記述することになります。

`cplat_file_stat_is_regular()` が、この差異を吸収します。  
引数の値だけを参照して OS へアクセスしないため、追加のシステム コールは発生しません。  
サイズの確認に使う `cplat_stat()` の結果をそのまま渡せます。

glibc が `S_IFMT` を `__USE_MISC` の内側へ置いていることと、MSVC が `S_ISREG()` を持たないことという、標準規格の外側の知識も、利用側は持たずに済みます。

### 最終更新日時の取得と設定

時刻の型は cplat の標準時刻型 `cplat_timespec` です。  
Linux は `st_mtim` と `futimens` および `utimensat`、Windows は `GetFileTime` と `SetFileTime` で実装しており、両 OS ともサブ秒を扱います。

本関数はこの API を次の 3 か所で使います。

1. **省略判定の入力**: 日時の比較はサブ秒で行います。`cplat_stat()` の `st_mtime` は秒精度のため比較には使いません。同じ秒のうちに更新されたコピー元を取りこぼしません。
2. **中断時の自己回復**: 失敗時にコピー先の日時をコピー開始前の値へ戻し、次回の呼び出しで再試行させます。
3. **成功時の日時の同期**: コピー先の日時をコピー元と同じ値に設定します。内容と日時の両方が一致した状態になり、2 回目以降の呼び出しは `SAMPLE_SKIPPED` になります。コピーの直後にコピー元が更新された場合の取りこぼしも起きません。

### 設定 API の共通契約

`cplat_file_set_modified_timestamp()` は書き込みアクセスで開いたハンドルを要求し、読み取り専用のハンドルには OS の API を呼び出さずに `CPLAT_ERR_PERMISSION_DENIED` を返します。

Linux の `futimens` は読み取り専用で開いた記述子でも、呼び出し元がファイルの所有者であれば成功します。  
厳しい側の Windows に合わせて事前に失敗させることで、両 OS の挙動をそろえています。  
cplat の「限界値は厳しい側に合わせる」共通契約に従う判断です。

## テスト観点

テストの構成は [テスト方法](../../../../framework/testfw/docs/how-to-test.md) と、cplat の `test/src/libcplatTest/crt/fileTest/` に倣います。

実ファイルを使う観点は次のとおりです。

- コピーが成立し、コピー先の内容がコピー元と一致する
- コピー元が存在しない
- コピー先が存在しない
- サイズが一致しない
- コピー元のほうが古い
- 最終更新日時が同値である
- 引数が NULL である
- コピー先が読み取り専用である
- コピー先がディレクトリである
- 転送バッファーの境界となる 64 KB ちょうどと 64 KB + 1 バイト
- 同じ引数で 2 回呼び出したとき、2 回目が `SAMPLE_SKIPPED` になる

`mock_cplat` を使う観点は次のとおりです。

- `cplat_file_read()` が要求より少ない量を返す場合に、繰り返して全量を転送する
- `cplat_file_read()` または `cplat_file_write()` が途中で失敗した場合に `SAMPLE_ERR` を返す
- `cplat_calloc()` が失敗した場合に `SAMPLE_ERR_OUT_OF_MEMORY` を返す
